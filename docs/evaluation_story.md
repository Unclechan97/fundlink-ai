## 二、问题背景："凭着感觉上线的 AI"

FundLink 是信贷资金方接入平台，AI 模块负责自动把银行接口文档（放款/授信/还款）解析成可执行的 FreeMarker 模板和流程配置。核心链路是一个 **Agent Loop 状态机**：

```
接口文档 → ANALYZE(LLM解析字段映射) → VALIDATE(模板渲染验证) → DRYRUN(流程干跑) → PUBLISH(发布)
                ↻ 最多 3 轮自动重试，失败后人工决策（EDIT_AND_RETRY / SKIP / ABORT）
```

技术栈：Spring Boot 3.2 + 4 个 LLM Provider（Qwen/DeepSeek/SiliconFlow/Claude）+ Qdrant RAG + React 前端。

**上线两周后，三个痛点逐渐暴露：**

1. **模型效果不可比。** 同一个接口文档用 Qwen 解析出 12 个字段，用 DeepSeek 出 15 个。产品问"哪个准"，研发说"感觉差不多的"——没有任何数字支撑判断。
2. **RAG 检索"静默失效"。** 用户反馈模板渲染报错，排查发现 LLM 编造了 `repayData.repayType` 这个不存在的字段路径。根因是 RAG 检索到的"历史成功案例"和当前场景无关，但 LLM 照样采信了。
3. **Prompt 迭代靠猜。** 改了 Prompt 里"嵌套对象展开"的规则描述，上线后才发现某些边界 case 退化。没有任何回归机制。

**最致命的问题是心态层面——团队对 AI 系统的心态是"它能用就行"，而不是"我知道它有多好，也知道哪里还不够好"。**

## 三、行动过程

### 阶段一：不急着建框架，先看数据（第 1 周）

我的判断是：**评估体系不能凭空设计，得先搞清楚"哪里最值得评"。** 好消息是这个系统已经建了三张审计表：

- `ai_llm_audit` — 每次 LLM 调用的 provider、model、token、延迟、费用、成功/失败
- `ai_agent_trace` — 每个阶段的输入输出、耗时、状态
- `ai_feedback` — 用户修正前后的差异

我从这三张表拉了两组数据：

**数据 1 — LLM 调用质量（按 provider 分组）：**

| Provider | 模型 | 失败率 | P95 延迟 | 月度成本占比 |
|----------|------|--------|----------|-------------|
| qwen | qwen-plus | 2.1% | 5.2s | 47% |
| deepseek | deepseek-chat | 0.5% | 3.1s | 32% |
| siliconflow | Qwen/Qwen3-8B | 8.7% | 12.4s | 21%（免费但重试多） |

**立刻暴露的问题：SiliconFlow 虽然免费，但 8.7% 的失败率导致大量重试，实际总成本反而更高。而且 SmartRouter 把它分配给了 diagnosis 任务——诊断阶段本身就容易出错，Provider 再不稳定，雪上加霜。**

**数据 2 — Agent Loop 任务流转：**

```
任务成功率:   60%  (12/20 PUBLISHED, 6 FAILED, 2 ABORTED)
首次通过率:   35%  (第 1 轮即成功)
平均轮次:     1.8  (成功任务平均重试次数)
人工干预率:   40%  (触发 DECISION_POINT 的比例)

各阶段失败分布:  ANALYZE 45% | VALIDATE 30% | DRYRUN 25%
```

**两个发现：** (1) ANALYZE 阶段是最大瓶颈——占了近一半的失败，而 ANALYZE 的输入包含 RAG 检索结果；(2) 40% 的任务需要人工介入，说明 AI 的置信度不足以自主决策。

**基于数据，我确定了评估建设的优先级：RAG → ANALYZE → VALIDATE → E2E。** 按数据流方向，上游质量决定下游结果。

### 阶段二：RAG 三层评估体系（第 2-3 周）

**为什么从 RAG 开始？** ANALYZE 阶段的 Prompt 拼接了 RAG 检索到的历史成功案例。RAG 返回错误上下文 → LLM 基于错误信息做判断 → 后续三个阶段全部建立在不可靠的基础上。先保证上游的输入质量，再谈下游优化。

#### 技术选型：为什么不直接用 RAGAS

我做了三种方案的对比评估：

| 方案 | 思路 | 问题 |
|------|------|------|
| RAGAS 库 | 调 `ragas.evaluate()` | 依赖 12 个包（langchain、datasets 等）；0.1→0.3 API 不兼容；OpenAI embedding 和 BGE-small 对齐差 |
| 纯 LLM 打分 | Prompt 直接评 | 同一输入两次差 ±1 分，无法用于 A/B 测试 |
| **手写 L1/L2 + LLM L3** | 自己控制每层 | 需要自己写指标公式，但完全可控 |

选了手写方案。核心理由：**评估用的 embedding 模型必须和检索用的一致**——用 OpenAI embedding 测出 0.9 但 BGE-small 检索不到，就是自欺欺人。

#### 三层模型设计

```
┌──────────────────────────────────────────────────────────┐
│ L1：目标断言（确定性计算）                                  │
│   目标文件是否在 top-8 结果中？在哪个位置？                  │
│   纯代码，零成本，跑一次 2 秒                               │
├──────────────────────────────────────────────────────────┤
│ L2：排序质量（BGE-small embedding，和检索同模型）           │
│   检索结果和地面真值的语义相似度（avg / max / 分布）         │
│   用于对比"哪个检索模式排序更好"                            │
├──────────────────────────────────────────────────────────┤
│ L3：LLM 裁判（DeepSeek-chat, temperature=0）              │
│   Faithfulness：答案是否基于上下文（不编造）?  1-5 分       │
│   Answer Relevancy：答案是否回应问题?           1-5 分      │
│   只在趋势监控时用，不用于精确 A/B（非确定性 ±1 分）         │
└──────────────────────────────────────────────────────────┘
```

#### 标注数据：踩过的坑

第一版 10 条测试用例是根据设计文档推测的。比如写了 `"预期文件": "加解密算法规范.md"`，地面真值写了"SM4 用 CBC 模式"。跑完 eval 才发现真实文件里根本没有"SM4"这个词——地面真值完全是脑补的。

**教训：标注数据不能推测，每条 ground_truth 必须逐字对照原文档验证。地面真值的质量比评估算法本身更重要。**

重写了 20 条用例，覆盖 6 个业务领域（财务部、风控部、贷前/贷中/贷后、公共通用），每条都读了原文档确认。

#### 第一次跑分：抓出两个生产级 Bug

运行 `python eval/eval.py --mode hybrid --skip-l3`，L1 只有 80%。排查发现两个问题：

**Bug 1 — 测试数据 domain 和系统不一致。** 标注了 `"domain": "financial"`，但 Qdrant 里实际存的是 `"financial/fin-server"`。exact match 全部过滤，返回 0 条。→ 修复：统一 domain 命名规范。**L1: 80% → 90%。**

**Bug 2 — 索引过滤规则误杀了 5 个业务文档。** `should_index()` 里有一条子串匹配规则 `"规范.md"`，本意是排除编码规范模板。但 `"规范.md" in "加解密算法规范.md"` → True，导致 5 个真实业务文档从未被索引过。这个 Bug 从系统上线第一天就存在，**但没人发现——因为用户不会去搜一个自己不存在的文档。**

→ 修复：删掉过度兜底规则，改为精确排除。重建索引（188 文件，6205 chunks）。**L1: 90% → 100%。**

> **这个发现改变了我对评估的理解：好的评估不只是"证明好"，更是"发现坏"——而且是那些用户反馈无法暴露的坏。**

#### 迭代 15 轮：选出最优检索模式

对比了三种检索模式（hybrid 混合检索 / rerank 精排 / adaptive 自适应）：

| 模式 | L1 Recall | L2 Relevancy | L3 Faithfulness | 结论 |
|------|-----------|-------------|-----------------|------|
| hybrid | 100% | 0.62 | 4.8 / 5.0 | 覆盖好，排序一般 |
| **rerank** | **100%** | **0.69** | — | **覆盖好 + 排序好 → 生产选用** |
| adaptive | 85% | 0.80 | 5.0 / 5.0 | L2 最高但漏 15% 的正确答案 |

**选型思考：** adaptive 的 L2 最高（0.80），但 L1 只有 85%——它在 15% 的 query 上返回了 0 条结果。对于信贷业务，"找不到"比"排序差"严重得多。所以在覆盖和精度之间，我选了 rerank——L1 100% + L2 0.69，不丢答案的前提下排序最好。

**RAG 评估阶段收效：**
- L1 Recall: 80% → **100%**
- L2 Relevancy: 0.59 → **0.69**（+17%）
- L3 Faithfulness: — → **4.8/5.0**（几乎不编造）
- 发现并修复 2 个隐性 Bug
- 确定了 rerank 为生产检索模式

### 阶段三：架构约束优化 — 减少 AI 的犯错空间（第 4 周）

在做 Agent Loop 评估的同时，我做了一个看似"产品体验优化"但本质上改变了评估格局的改动。

#### 背景：AI 直接生成 FreeMarker 模板的问题

系统原来的流程是：LLM 在 ANALYZE 阶段直接输出完整的 FreeMarker 模板字符串，包含嵌套对象、`<#list>` 循环、`${}` 变量引用。然后 VALIDATE 阶段调 Preview API 验证模板能否渲染。

这个方案有两个深层问题：

1. **LLM 被要求同时处理两件事** — 语义理解（"申请金额应该映射到 `loanInfo.amount` 还是 `approveAmount`？"）和语法构造（"嵌套 3 层的 JSON 大括号怎么写？`</#list>` 闭合了吗？"）。前者是 LLM 擅长的，后者是人都不擅长的。

2. **出错了分不清根因** — Preview API 报 FreeMarker 渲染失败，你分不清是 LLM 把 `</#list>` 写成了 `</list>`（语法错误），还是 `sourcePath` 指向了不存在的字段（语义错误）。排查链路从"哪个映射错了"变成了"整段模板哪里写错了"。

**更关键的是对评估的影响：** VALIDATE 阶段的评估被语法问题和语义问题混在一起。评估报告说"20% 的模板渲染失败"——这个数字毫无指导意义，因为你不知道该优化 Prompt（解决语义问题）还是加语法校验（解决格式问题）。

#### 方案：字段映射 + 程序构建模板

我把流程拆成了两段：

```
改之前: LLM → FreeMarker 模板 (高自由度，错误类型混杂)

改之后: LLM → 字段映射 JSON          → ConfigWriter → FreeMarker 模板
         (AI 负责语义理解)              (确定性系统负责语法构造)
         
  字段映射示例:
  {"fundField": "custName",   "sourcePath": "userInfo.realName", "transform": null}
  {"fundField": "loanAmount", "sourcePath": "loanInfo.amount",   "transform": "formatAmount"}
  {"fundField": "items[].sku","sourcePath": "paymentData.sku",   "transform": null}
```

ConfigWriter 的逻辑是确定性的——根据点号路径递归构建嵌套 JSON，遇到 `[]` 标记就生成 `<#list>` 循环。`buildTree(字段列表) → writeNode(树节点) → FreeMarker 字符串`。这个算法不涉及 LLM，100% 可测试。

#### 这个优化带来的三层影响

**第一层：模板语法错误从概率事件变成了不可能事件。**

ConfigWriter 不会写错 `</#list>`，不会漏掉闭合大括号，不会搞错 `${}` 的变量名。这部分问题被彻底消灭了。

**第二层：评估焦点从"对不对"升级到"好不好"。**

```
改之前: VALIDATE 评估 → 模板语法对吗？能渲染吗？字段映射对吗？
         (三个问题混在一起，评估结果无法指导优化方向)

改之后: ConfigWriter → 单元测试保证（确定性系统，不需要 AI 评估）
        VALIDATE 评估 → 纯语义问题：字段覆盖全了吗？sourcePath 存在吗？transform 选对了吗？
         (聚焦 LLM 真正容易出错的地方)
```

Preview API 再报渲染失败——那一定是映射的语义问题，不是模板语法问题。排查效率从"整段模板里找 bug"变成了"定位到具体那条映射"。评估的 Golden Set 也不用包含完整的模板字符串了，只需要标注"这个接口应该有 12 个字段，分别映射到这些 sourcePath"。

**第三层：确立了"约束即质量"的 AI 产品设计原则。**

这个改动背后是一个更通用的设计模式：

```
AI 输出自由度 vs 错误率的关系:

高自由度 (生成 FreeMarker 全文) → 错误类型多、排查难、评估难
中自由度 (生成字段映射 JSON)   → 错误类型少、排查快、评估聚焦
低自由度 (选择已有模板)        → 几乎没有错误、但灵活性差

最优解是"中等自由度"——在灵活性和可靠性之间取平衡。
```

这和几个行业实践是同源的：

| 实践 | 本质 | 我的做法 |
|------|------|----------|
| **OpenAI Structured Outputs** | 约束 token 级别的输出格式 | 约束字段级别的输出结构 |
| **编译器 IR** | 源码 → 中间表示 → 目标代码 | 接口文档 → 字段映射(IR) → FreeMarker(目标代码) |
| **Anthropic Tool Use** | 不让 LLM 执行操作，让它描述操作 | 不让 LLM 写模板，让它描述映射关系 |

**ConfigWriter 本质上是一个"模板编译器"——AI 生成中间表示（字段映射），编译器把它编译成目标代码（FreeMarker）。** 编译器是确定性的、可验证的、不依赖 AI 的。

#### 对评估策略的启发

这个优化还揭示了一个评估资源分配的原则：**不是所有东西都需要 AI 来评估。**

```
确定性系统 → 单元测试就够了  (ConfigWriter: 10个用例覆盖嵌套/数组/空路径/transform)
LLM 输出   → 需要 AI 评估     (字段映射的语义正确性)
规则可判   → 规则就够了        (FieldCompletenessGuard: 字段数量对不对)
```

不要用 LLM-as-Judge 去评估那些可以用规则验证的东西。把评估资源花在刀刃上——只有语义理解需要 LLM 时才用 LLM。

**这个阶段的收效：**
- 模板语法错误: **完全消除**（从概率事件变为不可能事件）
- VALIDATE 阶段评估价值: **从"查语法"升级到"查语义"**
- 出错排查效率: 从"整段模板找 bug"变成"定位具体映射行"
- 评估 Golden Set 标注成本: 不需要完整模板字符串，只需要字段级标注
- 为后续的 E2E 评估扫清了障碍——VALIDATE 阶段的失败原因可追溯、可量化

### 阶段四：Agent Loop 端到端评估（第 4-5 周）

RAG 和架构约束都就位后，开始对 Agent Loop 全链路做端到端评估。不需要从零建数据集——**已有的三张审计表就是最好的数据源。**

#### 建立 4 个 E2E 指标

```sql
-- 不需要额外埋点，从 ai_task 和 ai_agent_trace 直接算
任务成功率    = COUNT(PUBLISHED) / COUNT(ALL)           -- 目标 > 85%
首次通过率    = COUNT(rounds=0 & PUBLISHED) / COUNT(PUBLISHED) -- 目标 > 50%
平均轮次      = AVG(current_round) WHERE status='PUBLISHED'   -- 目标 < 1.5
人工干预率    = COUNT(DECISION_POINT) / COUNT(ALL)      -- 目标 < 20%
```

**初始基线：** 任务成功率 60%，人工干预率 40%，平均 1.8 轮。

#### 两个针对性优化

**优化 1 — 诊断规则引擎降低误判。** 系统有 5 条规则引擎（字段映射缺失 0.92 / FreeMarker 0.85 / SpEL 0.82 / 数据源 0.80 / enumMap 0.78），confidence ≥ 0.7 直接返回。但发现一个问题——规则把用户故意留下的 TODO 占位符（`sourcePath=""`, `remark="TODO:需人工确认"`）也诊断为"字段缺少映射"，触发不必要的重试。→ 加了 `isTodoPlaceholder()` 判断。规则命中率从 72% 提升到 88%，无效重试减少 40%。

**优化 2 — 模型路由调整降低诊断失败率。** SmartRouter 原来把 diagnosis 任务路由到 SiliconFlow（免费模型 Qwen/Qwen3-8B），但它的失败率 8.7%。切换为 DeepSeek（deepseek-chat，失败率 0.5%）。虽然单次调用费用从 $0 变成 $0.0003，但 eliminates 了 "diagnosis 失败 → fallback → 多一次 LLM 调用" 的浪费。**整体成本下降 30%，诊断延迟减少 60%。**

#### 引入 LLM-as-Judge 做在线评分

每次任务完成后，让 Judge 从三个维度打分（1-5）：
- **字段完整性**：是否覆盖了文档中的所有字段？
- **映射合理性**：sourcePath 和 transform 是否正确？
- **整体可用性**：该配置能否直接用于生产？

Judge 用 DeepSeek-chat 独立调用，不经过 SmartRouter（保证评分标准一致）。评分结果写入 `ai_eval_result`，作为在线质量趋势的数据源。

**Agent Loop 评估阶段收效：**
- 任务成功率: 60% → **87%**
- 首次通过率: 35% → **52%**
- 人工干预率: 40% → **18%**
- 平均轮次: 1.8 → **1.3**
- 诊断延迟: 4.5s → **0.3s**（规则命中场景）
- LLM 月度成本: 下降 **30%**

### 阶段五：建立评估驱动迭代闭环（第 6 周）

前面三个阶段建好了评估能力，但评估的真正价值在于**融入日常迭代**。

我设计的闭环：

```
┌────────────────────────────────────────────────────────┐
│  Prompt 变更  →  L1/L2 全量回归 (20条, ~5min)          │
│  模型切换     →  L1/L2/L3 新老对比 (同数据集, 同条件)    │
│  RAG 入库     →  L1/L2 检索质量回归                     │
│  每周日 Cron  →  E2E 成功率 + Judge 评分趋势报告        │
│  用户负反馈   →  逐阶段复盘 → 回写 ai_feedback          │
│                                                       │
│  核心原则：有变更必评估，有上线必回归                     │
└────────────────────────────────────────────────────────┘
```

具体落地了三件事：

1. **CI 集成**：Prompt 变更 → GitHub Actions 自动跑 RAG 全量 eval → L1 < 100% 或 L2 下降 > 5% → 拦截合并。**防止了 3 次 Prompt 退化提交。**

2. **评估数据库**：新建 `ai_eval_dataset`（金标准数据集）和 `ai_eval_result`（评估记录），每次评估跑分可追溯、可对比。配合已有的 3 张审计表，形成了完整的"采集→评估→优化→验证"数据闭环。

3. **周报自动化**：每周日 Cron 从 `ai_eval_result` 聚合趋势，飞书消息推送。当 Judge 评分连续两周下降 > 0.3 分时自动告警。

## 五、面试高价值论点

以下是建议在面试中主动抛出的观点，每个都有具体的"故事→数据→反思"支撑：

### 论点 1："评估要先看数据再建体系，不能反过来"

很多团队一上来就说"我要用 RAGAS + DeepEval + LangSmith 建一套完整评估"。我做的第一件事是从已有的审计表拉数据——一行 SQL 就发现 SiliconFlow 失败率 8.7% 但被分配做关键任务。**没有这一步，建再多评估指标也是自嗨。评估只是手段，找到优化方向才是目的。**

### 论点 2："好的评估不只是证明好，更是发现坏"

EXCLUDE_PATTERNS 误杀 5 个业务文档的事——这个 Bug 从上线第一天就存在，但用户反馈永远不会暴露它（因为用户不知道有这个文档）。是离线评估第一次跑就抓到的。**没有 eval 的过滤规则，和没有断言的代码一样——你以为它在保护你，其实它在悄悄删数据。**

### 论点 3："评估指标之间也有盲区"

adaptive 模式 L2=0.80 最高，但 L1 只有 85%。如果只看 L2（Context Relevancy），你会选 adaptive——它返回的内容确实最相关。但 L1 暴露了它在 15% 的 query 上返回了 0 条结果。对信贷业务，"找不到"比"排序差"严重 100 倍。**单一指标会骗你，指标体系之间的交叉验证才是真正的质量保障。**

### 论点 4："评估模型和检索模型必须一致"

用 OpenAI embedding 做 L2，但检索用 BGE-small → 评估说好但检索不到 → 自欺欺人。**评估的可信度取决于评估环境和生产环境的一致性。** 这不是技术选型问题，是评估哲学问题。

### 论点 5："LLM-as-Judge 不用于 A/B，用于趋势"

Haiku 评分同一输入跑两次差 ±1 分。所以我的 L3 只用于周度/月度趋势监控（Faithfulness 从 4.8 掉到 3.5 就要警惕），精确的 A/B 决策靠确定性的 L1/L2。**每个指标都要定义它的"决策半径"——哪些能用它拍板，哪些只能用它参考。**

### 论点 6："地面真值质量 > 评估算法复杂"

第一版测试用例因为推测 ground_truth 而全废。这件事让我理解了为什么标注数据的质量是评估体系的基石——**算法可以换，框架可以迭代，但地面真值错了，所有指标都是垃圾。**

### 论点 7："评估之前先做架构优化——减少 AI 的犯错机会比评估错误更有价值"

很多团队的做法是 AI 输出什么就评估什么。我的经验是先问自己一个问题：**这个输出里，哪些是 AI 不该负责的？** FreeMarker 模板的语法构造就属于这一类——它是确定性规则可以保证的事，不应该交给 AI 去"试"。我把 LLM 的输出从"完整的 FreeMarker 模板"改成"结构化的字段映射 JSON"，再用 ConfigWriter 确定性构建模板。结果是语法错误系统性消灭了，评估焦点也从"语法对不对"升级到"语义对不对"——后者的评估价值高得多。**这背后是一个 AI 产品设计原则：通过约束输出空间来消除整类错误，而不是靠评估去发现错误。**

### 论点 8："评估资源要分级——不是所有评估都要全量跑"

我的三层设计本身就是成本分级：L1 零成本 2 秒跑完，适合每次 commit；L2 多 30 秒，适合每日构建；L3 需要 LLM 调用、有成本、有波动，适合每周趋势。**评估体系好不好，不是看指标全不全，是看能不能以最低成本在正确的时间点给出正确的决策信息。**

## 六、如果被追问"还有什么不足"

坦诚说出当前局限反而加分：

1. **标注数据量还不够** — 20 条能看出趋势，但差一条 = 差 5 个百分点，统计置信度不够。计划扩展到 50 条做可靠的 A/B 测试。

2. **缺少对抗评估** — 现在的测试集都是"正常"文档。没有故意构造的边界 case（格式混乱、字段歧义、50+ 字段的大文档）。对抗评估能暴露模型的鲁棒性问题。

3. **E2E 评估依赖人工标注** — 建一条完整的 Golden Set（文档→期望字段列表→期望模板→期望流程）需要 20-30 分钟。目前只有 ANALYZE 阶段的字段级标注。

4. **缺乏线上评估** — 离线评估只能告诉你"系统和昨天比有没有退化"，不能告诉你"用户的真实感受"。计划从 `ai_feedback` 的 diff_summary 自动提取高频修正模式，作为在线评估的信号。

5. **Judge 的非确定性** — LLM 评分有 ±1 分的波动。目前只能接受这个误差、把它限定在趋势监控场景。更理想的方案是多次采样取中位数，但成本 ×3。

## 七、总结：一句话版本

> "我从 0 到 1 建了 FundLink AI 的评估体系。第一步不是建评估框架，而是从已有审计数据里找瓶颈——发现 ANALYZE 阶段占了 45% 的失败，根因在 RAG。于是从 RAG 三层评估（L1 断言 / L2 排序 / L3 LLM 裁判）切入，15 轮迭代把 L1 Recall 从 80% 拉到 100%，同时抓出 2 个隐形数据 Bug。第二步做架构约束——把 LLM 的输出从 FreeMarker 模板收窄为字段映射 JSON，用确定性系统构建模板，消灭了整类语法错误。第三步把评估推到 Agent Loop 端到端，通过模型路由调整和规则引擎优化，把任务成功率从 60% 提升到 87%，人工干预率从 40% 降到 18%。最终把评估集成到 CI，形成'有变更必评估、有上线必回归'的闭环。最大的收获不是指标，而是三个认知——评估之前先做架构减负（减少 AI 的犯错空间），评估指标要交叉验证（单一指标会骗你），评估成本要分级（不是所有东西都需要 LLM 来评估）。"

# 04 — 边缘场景与兜底方案

> 优先级: 贯穿所有 Phase
> 覆盖 10 个边缘场景，每个都有明确的兜底路径

---

## 场景 1：拆分只识别出 1 个接口

**可能原因**：文档确实是单接口；文档格式不标准，拆分规则没命中。

**兜底**：
1. N=1 → 直接交给 `RequirementAgent` 处理（退化为现有逻辑，零额外开销）
2. LLM 校验发现应该有多个接口 → 降级到 LLM 拆分

---

## 场景 2：拆分识别出太多接口（> 20）

**可能原因**：文档包含大量 API（如 OpenAPI spec）；拆分规则过度匹配。

**兜底**：
1. N > 20 → 暂停，返回接口列表让用户确认
2. 前端展示"检测到 35 个接口定义，是否全部处理？"
3. 用户可选择部分接口
4. 上限 `max-count: 50`，超过则拒绝自动处理

---

## 场景 3：拆分出两个完全相同的接口

**原因**：同一接口在不同章节被描述（如概览 + 详细定义）。

**兜底**：
1. 去重阶段自动合并，保留 `sectionText` 更丰富的版本
2. 前端提示 "检测到重复接口定义，已合并"
3. 用户可查看被合并的原始文本（展开详情）

---

## 场景 4：名称相似但端点不同的接口

**原因**："放款申请（JSON）"和"放款申请（XML）"，或不同版本。

**兜底**：
1. **不去重**（端点不同 = 不同接口）
2. 在 `interfaceName` 中保留区分信息
3. 生成不同的 Template Code

---

## 场景 5：并行处理中某个接口超时/失败

**原因**：LLM 超时、解析失败、写入 FundLink 失败。

**兜底**：
1. 单个失败不影响其他（`exceptionally` 隔离）
2. 每个接口独立状态：`SUCCESS` / `FAILED` / `TIMEOUT`
3. 前端展示每个接口独立状态 + 失败原因
4. 用户可对失败接口单独重试
5. **全部失败 → 降级为全文档单接口处理**

---

## 场景 6：并行写入时 Provider 冲突

**原因**：所有接口共享同一 Provider，并发写可能竞态。

**兜底**：
1. Provider **先同步创建**（在所有并行任务启动前），一次性完成
2. Template/Flow/Mappings 在 Provider 创建后才并行写入
3. Provider 的 `findByCode → 复用` 逻辑本身幂等，双重保障

---

## 场景 7：接口之间存在依赖关系

**原因**：接口 A 的响应字段是接口 B 的请求字段（如 loanNo）。

**兜底**：
1. 当前版本：拆分时不考虑依赖（每个接口独立处理）
2. 每个接口生成独立 Flow
3. 依赖关系在后续"流程拼接"阶段处理（未来功能）
4. 用户可手动关联

---

## 场景 8：意图识别误判

**原因**：文档措辞偏向说明性，或 LLM 判断失误。

**兜底**：
1. 前端展示识别结果 + 置信度
2. 用户一键切换意图（按钮：不是接口文档？）
3. 切换后重新走对应 Handler
4. **置信度 < 0.7 → 前端弹确认框，强制用户确认**

---

## 场景 9：非标准格式文档（PDF 复制、OCR）

**原因**：格式混乱，无清晰结构。

**兜底**：
1. 程序化拆分失败（4 个策略都返回空）→ LLM 拆分
2. LLM 拆分也失败 → 全文档作为单接口处理
3. 前端提示"未能识别接口结构，将按单接口处理"

---

## 场景 10：拆分正确但字段映射质量差

**原因**：文档片段信息不足（缺少上下文字段说明）。

**兜底**：
1. 子 Agent Prompt 注入 GlobalContext（公共字段、枚举值）
2. 低置信度映射（confidence < 0.5）高亮标记
3. 手动模式下用户可编辑

---

## 通用兜底原则

1. **每一步都可回退**：拆分失败 → 单接口，并行失败 → 串行，全部失败 → 不阻塞用户
2. **状态透明**：前端始终知道当前进度和每个接口的状态
3. **用户可控**：意图可切换、接口可选、失败可重试
